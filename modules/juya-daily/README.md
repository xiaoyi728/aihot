# 橘鸦AI早报（modules/juya-daily）

把 [橘鸦AI早报](https://daily.juya.uk/) 的每一期拆成它自己的那几十条新闻，推进站里，并按期原样列出。

## 为什么不是一个普通的 rss 信源

它的订阅里，一期只有一条 item：标题是一个日期，链接指向整期页面，`content:encoded` 是整期的 HTML。
当普通信源收，就是把一天二十几件事收成一条一万多字的合集——评分提示词里「多事件打包且没有单一焦点」
把它压在门槛之下，它进不了精选，也永远进不了日报（日报只收已入选的报道）。

真正的每一条新闻只存在于那一页的 HTML 里，各自带分类、中文标题、**原文链接**和一百到六百字的中文正文。

## 它做什么

- `collect.ts`：读订阅（用 ETag，没出新一期时对方只回一个 304，不重复下载整份 0.5 MB），
  把还没入库的期拆开（`parse.ts`），每一条用**原文链接**作为资料地址连同橘鸦的中文标题和正文推进正常的
  流水线：和其他信源判重、评分、归组。官方源也在场时由官方那篇出面（引擎的权威序），橘鸦这条作为同一事件的
  另一篇参与热度和精选。
- 它自己的页面 `/juya`（`page.tsx`）：按期列出**全部**条目，按橘鸦自己的分类分组，不做事件去重——
  这是它独立出来的那一份清单。**日报页上不画它**：日报上的每一条都和其他信源一样，过了同一套评分与编排
  （同一门槛、同一归组、同一「同一信源最多两条」）。
- `server.ts` 的定时任务在 08:00–14:00 每十分钟问一次订阅（`COLLECT_ENABLED` 关着时不跑），
  以及「一天多没有新一期了」的提醒。

第一次运行只导入最新一期：更早的期数是回灌，会刷屏并花钱。

## 表格

`juya_issues`（期）、`juya_items`（条目）、`juya_feed_state`（订阅的 ETag），迁移在 `migrations/`。

## 相关

`industry/sources.json` 里那条 `rss-juya-ai-daily` 已停用（`enabled: false`）：同一个地址由这个模块读，
不停用会每小时重复下载一次整份订阅，并留下一条进不了精选的整期文章。
